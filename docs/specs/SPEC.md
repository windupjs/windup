# Windup — Living Specification

**Status:** implemented (describes the system as shipped in `windupjs@0.9.x`) · **Supersedes:** [SPEC-001](spec-001-post-spike-evolution.md) and [SPEC-002](spec-002-cli-and-indexing.md) (historical — fully implemented; measured results in `RESULTS-tranche-{1,2,3}.md` and `../spike/RESULTS.md`).

## 1. Thesis

Browser E2E tests can use an LLM **only for planning** (and re-planning on failure), with deterministic execution and cheap verification — so repeated runs make **zero LLM calls**. Validated end-to-end: first run plans in seconds for fractions of a cent; replays take ~0.5–1s and cost $0.

## 2. Principles

1. **The LLM is the exception, not the rule.** One call per cache miss; replays never call it.
2. **Zero hardcoded site knowledge.** The engine may know *frameworks* (Next.js, react-router, design-system naming conventions) and the web platform — never a specific site. All site knowledge arrives as input (scenario, config, manifest) or is discovered at runtime. Conformance check: `git grep -i "<any-site-name>" src/` must return nothing.
3. **Every execution is also collection.** The executor already visits every page of a flow; persisting what it sees costs ~one `evaluate` per action.
4. **Knowledge is cache, not truth.** Anything the site map or static scan asserts can be stale; it degrades to runtime discovery and is corrected by observation. Precedence: `execution > static > llm`.
5. **Cost never surprises.** Every LLM touchpoint has an explicit cap; every call is recorded in a ledger (`windup costs`); repeated static/assist work is memoized.
6. **Plans are data, not programs.** No conditionals, no loops, no free-form code. If a flow needs branching, split the scenario.

## 3. Architecture

```
scenario (natural language, versioned)
        │
        ▼                      site map (graph) ◀── windup scan (static + LLM-assist)
   ┌─ runner ─────────────────────────┐▲
   │ cache lookup (path-keyed)        ││ passive collection (every run)
   │   miss → planner (LLM, 1 call)   ││
   │   hit  → cached plan (rebased)   ││
   │        → executor (deterministic)┼┘
   │        → verifier (postconditions)│──▶ failure: invalidate → re-plan
   │        → cache save + run ledger │
   └──────────────────────────────────┘
```

| `browser.ts` | **Single engine boundary** (Playwright since 0.6). Sessions = fresh `BrowserContext` on a lazy per-process Chromium singleton (E5 pool: `--repeat`/`--all`/bench pay the launch once; warm-replay p50 ≈ 415ms). Trusted clicks with native actionability. Native dialogs: `armDialog(accept|dismiss)` registers a one-time `page.once('dialog')` handler before the triggering action (Playwright otherwise auto-dismisses, so a `confirm()`-gated mutation never runs). The plan action carries `dialog?: "accept"|"dismiss"`; the planner emits it for confirm/alert/prompt steps and prefers persistent verification signals over ephemeral toasts. **Per-scenario dialog default (`on_dialog`):** `setDialogHandler(accept|dismiss)` installs a **persistent** `page.on('dialog')` for the whole run (every native dialog answered, no per-action field) — set once from `Scenario.on_dialog`; when present `armDialog` no-ops so the persistent handler wins. **Accessibility-label fallback:** `clickByDescription`/`fillByDescription`/`isVisibleByDescription` locate a target by its accessible name (`getByLabel`/`getByPlaceholder`/`getByRole("textbox")` on the cleaned description) and act only when **exactly one visible** element matches — the executor's recovery path when a plan selector misses. `ariaSnapshot()` (YAML) feeds the planner. Target policy: the first VISIBLE match, not the first DOM match — text selectors (`:has-text`) also match hidden items (closed menus, command palettes) that precede the real control in DOM order. Cross-browser since 0.20: `chromium` (default, auto-provisioned) | `firefox` | `webkit`, selected per run (`--browser` / `WINDUP_BROWSER`) or in config; firefox/webkit are opt-in (`npx playwright install <name>`), a plan replays across all three (CSS selectors are engine-agnostic). Swapping engines has twice been a one-file change — keep it that way. **Request stubbing (`config.network`):** in `launchBrowser`, before `newPage`, a `context.route("**/*")` matches each request against author-declared rules (`network.ts` `matchRule`: url substring-or-glob + optional method, first match wins) and `fulfill`s a `status`/`body`/`json` response or `abort`s it — a deterministic 500 / empty-list / dropped-request without a backend. **Frozen clock (`config.clock`):** `now` freezes `Date`/`Date.now()` via `addInitScript` (a plain interpolated STRING, not a serialized function — a downleveled `class extends` would drag in a page-absent helper) so `new Date()` in the app returns the fixed instant; `timezone` sets the context `timezoneId`. Both apply on every launch and, absent a per-scenario override, are read from `getContext().config`; `launchBrowser({ network, clock })` opts take precedence (the runner passes a scenario's `network`/`clock` merged over the global config — see `scenario.ts`), and the effective network is stored on the session so `captureDiagnostics` excludes per-scenario-stubbed 5xx too. Never enter the cached plan, validated eagerly (`validateNetwork`/`validateClock`, also surfaced in `windup doctor`). **Runtime diagnostics (`config.failOn` / `--fail-on-console` / `--fail-on-resource` / `--fail-on-5xx`):** passive `page.on("console"/"pageerror")` + `page.on("response")` listeners installed at launch (`captureDiagnostics`) accumulate console errors and 5xx responses; `requestfailed` is deliberately NOT listened to (a `config.network` `abort` fires it) and responses matched by a `config.network` rule (a deliberate stub) or `failOn.ignore` are excluded. Each console error is captured as a `ConsoleError { message, url?, kind }`: `url` from `console.location().url` (the failing resource for a load error, absent for `pageerror`), `kind` from `classifyConsoleError` (`diagnostics.ts`) — `resource` when the message is the generic Chromium "Failed to load resource …", else `js` (exception / `console.error` / CSP). `failOn.ignore` is matched by `matchesIgnore` against **message AND url** (a resource error's console text has no URL, so URL-matching is the only way `ignore: ["gravatar.com"]` can silence it — and, unlike before, `ignore` is now applied to console errors at all, not only to 5xx). **Deliberate stubs are excluded from BOTH listeners**: the response listener uses `matchRule` (url+method); the console listener uses `stubMatchesUrl` (url only — a console error carries no method) against the session's **effective** rules (global + per-scenario merged, threaded via `launchBrowser({ network })`), so a per-scenario `{ status: 500 }` no longer trips `resourceErrors`. A resource error also records its numeric `status` (`resourceStatus` parses the Chromium message). Drained via `consoleErrors()`/`failedResponses()`; the runner splits them `jsErrs`/`resourceErrs` and records all in `RunMetrics.diagnostics` (always, informational like a11y — `console_errors: {message,url?,kind,status?}[]`). When the flag/config is on it flips a passed run to failed with a `"diagnostics"` `FailureKind`, evaluated against `effectiveFailOn` (`Scenario.failOn` merged over global — booleans win, `ignore` concatenated, the effective `ignore` threaded via `launchBrowser({ ignore })`): `consoleErrors` gates `js` only, `resourceErrors` gates `resource` only, `http5xx` gates 5xx — set directly (no cache invalidation, no re-plan), excluded from `RETRYABLE`, before the snapshot save and `--suggest`/`--summary`. **Device emulation (`config.device` / `--device`, `device.ts`):** a Playwright device preset (`resolveDeviceContext`) is spread into `newContext` (viewport/UA/scale/mobile/touch); the trajectory cache is namespaced by `deviceSuffix()` (`<id>@<slug>.json`) so viewports keep separate plans — empty suffix ⇒ byte-identical default paths. **Web vitals (`--web-vitals` / `config.budgets`, `vitals.ts`):** a buffered LCP+CLS `PerformanceObserver` init-script is injected before first paint; `webVitals()` reads navigation timing + FCP + LCP/CLS on the final page (both as transform-proof STRING scripts, same reason as the clock). The runner records `RunMetrics.web_vitals` and flips to a `"budget"` failure (same direct-set/non-retryable pattern) when `budgetViolations` finds a `config.budgets` breach. **Accessibility (`--a11y`):** `runAxe()` injects axe-core (an OPTIONAL dep, dynamic `import()`, kept out of the base install via tsup `external`; `npm i -D axe-core` to enable) and returns the final page's violations — informational, never fails the run. **`--shard i/n`** round-robin-splits the suite across CI runners; **`--watch`** re-runs a single scenario on file change (authoring). |
| `llm.ts` | **Multi-provider LLM boundary.** One `LlmClient` interface (prompt + schema + budget in, text + tokens + truncated out); implementations for Google Gemini (SDK, `responseSchema`, thinking off), OpenAI (plain REST — no SDK dependency; JSON mode + schema-in-prompt; `reasoning_effort: minimal` for reasoning models, `temperature`/`seed` for classic ones; configurable `baseUrl` covers any OpenAI-compatible endpoint), and `claude-code` (since 0.21, opt-in). Several providers configured simultaneously (`llm.providers` with per-provider default model and `apiKeyEnv`); selection per run: `--llm provider[:model]` flag → `WINDUP_LLM` env → legacy `LLM_MODEL` → config `llm.provider`+`llm.model`. Switching providers never touches the plan cache — plans are data. **`claude-code`** plans through the developer's own Claude subscription (no API token) — a gray area not endorsed by Anthropic, so opt-in and never a default. It has **two transports, chosen automatically**: with no URL configured (the default since 0.22) it **spawns the native `claude` CLI** in non-interactive print mode (`claude -p … --output-format json`) from an isolated temp cwd (loads no project `CLAUDE.md`; headless default permission mode cannot perform side-effecting tools) — zero setup, no server; with a `baseUrl`/`WINDUP_CLAUDE_CODE_URL` set it instead routes to [claude-code-openai-wrapper](https://github.com/RichardAtCT/claude-code-openai-wrapper), a third-party local HTTP proxy. Neither has a JSON mode, which forces two mechanical accommodations (prompt instructions alone were never enough anywhere in this codebase): the schema rides in the prompt and the reply is un-fenced by `extractJson` (drop ```` ```json ```` fences or dig the outermost `{…}` out of prose — Ajv stays the authority on validity); and `temperature`/`seed` are not sent (they have no CLI/wrapper equivalent; the seed jitter only ever mattered for flash-family degeneration). API key optional (`apiKeyOptional`); the CLI missing/not-logged-in, or a down wrapper, fails fast with an actionable `WindupError` instead of burning the transient-retry budget. **Key resolution** is one shared `resolveApiKeyEnv(provider)` (used by the client AND `doctor`, so the diagnosis cannot diverge): `llm.providers.<name>.apiKeyEnv` > the `llm.apiKeyEnv` shorthand > the provider default — the shorthand exists because that is where the generated config's comment sits and where everyone reaches first. **A provider 404 on the model name** is translated by `modelNotFoundError` into an actionable `WindupError` (naming known models from `PRICING.models`) rather than surfacing raw provider JSON; the runner then classifies any `WindupError` from planning as `FailureKind: "config"` — excluded from `RETRYABLE`, so `--retries` never repeats a misconfiguration as if it were a flake. |
| `planner.ts` | **Planning logic** (provider-agnostic, calls `llm.ts`). Prompt = task + initial-page a11y tree + real interactive elements + site-map slice + fragment catalog + project manifest + scenario hints. Structured output (`responseSchema`), thinking off, temp 0.3. Two retry levels: *semantic* (invalid plan → 1 retry, short prompt with plan+errors) and *transient* (model degeneration/network → up to 3 re-calls with varied seeds) — up to 2×3 calls per `generate()`. A **truncation is retried differently, not identically**: once a reply hits the output ceiling, every later call in that round raises the budget (`MAX_OUTPUT_TOKENS` 8k → `RETRY_OUTPUT_TOKENS` 16k) and the error says what to do (very large prompt → narrow the task, switch model) — re-sending the same request with the same ceiling is the retry least likely to help, and truncation (not task difficulty) is what drives the expensive path on element-heavy pages. Each extra call records WHY (`invalid plan: …` / `truncated response` / `invalid JSON` / `network/quota`) into `retry_reasons` → `RunMetrics.plan_retry_reasons`, printed under the run line (`planner retried 2× — …`): a 4-call, 60-second re-plan is now explainable instead of an unexplained `llm_calls=4`. Output is sanitized (empty/`"undefined"` fields, per-type field pruning, id renumbering, `wait_for`⇄`expect` normalization) then validated (Ajv full schema + semantic rules + `value_ref` allow-list). Cross-provider hardening from live A/B (2026-07-13): an explicit minimal-plan prompt rule (gpt-5 models tended to add steps beyond the task), and mechanical **fragment-echo dedupe** — actions right after a `use` that duplicate the fragment's own actions (type+selector) are dropped, preserving a trailing `expect`; prompt instructions alone did not hold across providers. A second live duel on complex scenarios (gemini-3.5-flash vs gpt-4o-mini) added the literal-credentials rule: when the task spells out credentials and cites no manifest account, the plan must use the task's literal values — weaker models were wrongly substituting manifest ENVs. Warns when a plan fills a password-like field with a value absent from task/hints/manifest (model-invented credential — login will fail far from the cause). When `scenario.atomic_steps` is set the prompt gains a **granularity rule** (one interaction per action, never merge a reveal/expand click with the action it uncovers — #2.1). Records provider+model into the plan's `generated_by` and the run ledger. |
| `executor.ts` | Deterministic loop: goto → per action (gate on visibility → **safety denylist** → act → verify postcondition). **Accessibility-label fallback (#2.2):** when the plan's selector doesn't become visible, click/fill/wait_for retry the target by its accessible name (`browser.*ByDescription`, exactly-one-visible-match); on success the action carries a `note` (`≈ found "<label>" by label (plan selector "<sel>" missed)`) surfaced in the report — recovering a brittle guessed selector without a re-plan. When neither selector nor label resolves, the error names the likely cause (control has **no accessible label — a11y gap**, anchor with a hint), so a failure doubles as an a11y finding. **`config.forbid` (#2):** before each action (and on the landing page), abort with a `forbidden` failure if the action's selector CONTAINS a `forbid.selectors` substring or the current/goto URL matches a `forbid.urls` path glob — a CI guardrail against irreversible side effects (change-password, delete, persist-config). Author-declared, never inferred (engine keeps zero site knowledge); a substring/glob match, not element resolution. A `forbidden` failure never invalidates the cache or re-plans (a deliberate block, not a broken plan) — so it needs no LLM key. **Readiness:** the start-page signature is taken as soon as EITHER interactive elements render OR the network goes idle (`browser.waitForIdle` / networkidle), whichever first, capped at 5 s — a display-only page no longer burns the full timeout every run (measured ~9× faster there; surfaced as `nav` in the breakdown). `SLOWMO_MS` demo pacing. Emits passive site-map observations. **Readiness gate (#4):** on entering a page whose URL matches a `config.readySignals` route glob, waits for the configured selector(s) to be visible before the first action there (start page and after cross-route navigation, deduped by URL). Deterministic, LLM-free, NOT part of the cached plan; best-effort (a signal that never shows warns and proceeds). Closes the load-time hydration race — element present but handlers not yet attached — that Playwright's per-element actionability can't detect (validated live: same plan fails without the signal, passes with it). |
| `runner.ts` (self-heal) | On a verification failure the cached plan is invalidated and re-planned with the provider that made it (`--llm` > recorded > config). The re-plan context is **guided** (#10): the exact failed selector with a do-not-reuse instruction, the scenario hints re-emphasized, and — under `--suggest` — the `generateFixSuggestion` diagnosis fed back into the prompt (surfaced once; not regenerated in the finally). A churn signal (≥2 recent `.stale-*` files) warns that the app likely lacks a stable selector or has a race rather than looping on LLM calls. **The caught regression outranks the self-heal** (`regressionWithReplanNote`): when the re-plan ALSO fails, its own problem (truncated reply, bad key) would otherwise overwrite `metrics.failure`, and the run would read `[plan_invalid] transient API failure` — "the tool hiccuped" — instead of the postcondition failure that is the actual finding. The verification failure is kept as primary (kind, action id, expected/actual intact) and the re-plan's trouble is appended as a `note:`. The tool's own trouble must never speak louder than the bug it just caught. |
| `verifier.ts` | Postconditions, all LLM-free, ANDed and polled to `timeout_ms` (frame-safe waits): `expect.selector` (visible), `expect.url` (glob or bare path vs pathname), `expect.selector_value`, and the richer kinds — `text_contains` ({selector,text}, substring of the element's text), `count` ({selector, equals/min/max} — raw `browser.count`, no visible filter), `not_visible` (a selector gone/hidden via `browser.waitForHidden`), `attribute` ({selector,name,value}). The empty-expect early-exit and the schema's final-action guard both enumerate ALL kinds (a plan whose only final assertion is a new kind must not be skipped/rejected). |
| `cache.ts` | Trajectory cache in `.windup/cache/trajetorias/` — **meant to be committed** (the "plan once, replay $0 anywhere" artifact: replays use the cached plan, so a committed cache runs the suite in CI / on any machine with no LLM and no planner CLI). Portable and secret-free: plans hold selectors + `value_ref` (never resolved values), and the hit key is environment-portable. `windup init` versions `cache/` + `map/` and gitignores only `state/`/`runs/`/`reports/`. Hit key: `scenario_id` + start-URL **path** (environment-portable) + versions + `status: active` + `scenario_sig` — a hash of the fields that SHAPE the plan (`task`, `hints`, `atomic_steps`, `depends_on`, `like`), so editing hints (how an author steers a bad plan) re-plans instead of silently replaying; runtime-only fields (`seed`/`network`/`clock`/`failOn`/`tags`/`on_dialog`/…) are excluded so editing them never costs a re-plan. Tolerant: entries without the field (pre-1.5.0) still hit, so upgrading never forces a paid re-plan of a committed cache. Save only after full verified execution. Failure in replay → entry renamed `*.stale-<ts>.json` (evidence, max 3) → full re-plan → stats accumulate (`plan_generation` flags unstable scenarios). Lenient signature check: `start_sig` mismatch warns (`sig_mismatch` metric), never blocks. Self-heal re-plans with the provider recorded in the failed plan's `generated_by` before the config default (precedence: `--llm`/`WINDUP_LLM` > recorded provider > config). |
| `session-cache.ts` | **Session snapshots (#4 — replay speed):** after a scenario runs, its **exit state** — Playwright `storageState` (cookies + localStorage) + final URL — is saved to `.windup/state/<id>.json` (**gitignored; holds auth cookies/tokens, never committed**). On a later CACHED replay whose dependency has a snapshot, the runner launches the context pre-seeded with that `storageState` (and gotos the final URL when the scenario continues from the dependency) and SKIPS re-running the `depends_on` chain (`deps≈0`, `reused_session_from` set) — removing the dominant wall-clock cost (re-login through the UI). Safe by the same gate as every plan: the restored replay is still verified; on failure (stale session / state not fully in storageState) the snapshot is dropped and the run FALLS BACK to a full-chain replay in a fresh context — `deferReplan` suppresses cache invalidation on the snapshot attempt so a good plan is never wrongly re-planned. Fast path is replays only (a first run plans anyway). `browser.ts` `launchBrowser({ storageState })` seeds the context; `storageState()` captures it. |
| `signature.ts` | Structural page identity (E1): interactive elements (tag/id/name/data-test/type), normalized, deduped, sorted, SHA-256 → `sig:<16hex>`. Never uses the a11y tree or text (environment/data variance). |
| `sitemap.ts` | Page/transition graph (`.windup/map/site-map.json`, atomic writes, JSON behind a `SiteMapStore` interface — SQLite deliberately deferred until scale demands). Nodes carry `source: execution|static|llm`, staleness, per-file provenance. Prompt slice: BFS (depth ≤ 3) from the current page over executed transitions, term-scored, then static and llm tiers fill remaining budget for uncovered URLs. Budgets: map ≤ 8k chars inside a ~32k-char combined context. |
| `scan/` | Project indexing. Layer 1: routes by convention/declaration (Next.js app+pages router; react-router JSX/object/lazy/v7 helpers/flat-file; TanStack Router file-based — createFileRoute id or file-name conventions: dot-notation, `$param`→`:param`, pathless `_` layouts, index/__root — wrapper-aware element resolution). Layer 2: interactive elements by brace-aware JSX parsing — raw tags **and** design-system components (Button/Input/Link/Label…, ecosystem naming conventions), harvesting id/name/data-test/type/aria/placeholder/`href`/`htmlFor`. Anti-inheritance: files declaring >2 routes never have imports expanded. Layer 3 (LLM-assist): heuristically selected unresolved files, hard `maxCalls` cap, per-file-hash memory (unchanged files are free forever), results marked `source: "llm"`, only kept when they add elements to an uncovered URL. Full scans reconcile: static nodes of removed routes and stale/duplicate llm nodes are pruned. `--update`: incremental via `git diff` since the recorded scan SHA; changed sources mark execution knowledge of the same URL stale until re-observed. |
| `fragments.ts` | Reusable tested sub-trajectories (E3), committed in `e2e/fragments/`. Plans reference `{ "type": "use", "use": "<id>" }`; the cache stores the *reference* (fragment updates propagate; orphaned references invalidate and re-plan). Expansion inline at run time, depth 1, ids renumbered. The planner sees only the catalog (id + description + postcondition), never the actions. Created via `windup fragment extract <scenario> <a1..aN>`. |
| `isomorph.ts` | **Isomorphic plan reuse (#1):** a scenario with `like: { scenario, set? }` reuses another scenario's PROVEN cached plan instead of an LLM call. `instantiatePlan` clones the source plan, rebinds identity + `start_url`, and applies `set` (source literal `value` → new `value`, on fill actions only — never selectors or `value_ref`); returns the plan + any unmatched keys (warned). The runner (miss path, before LLM) instantiates, expands fragments, then **executes + verifies** — cache the result as the scenario's own plan on success (`cache=hit`, `reused_from` set, `llm_calls=0`), else FALL BACK to LLM planning. Never invalidates the source, never bypasses the verify gate → cannot yield a silent false green (validated live: reuse passes on an isomorphic route, a non-isomorphic route fails verification and re-plans). Fragments reuse action BLOCKS; `like` reuses whole PLANS. |
| `authoring.ts` | **Scenario generator** (`windup new "<rough instruction>"`): the LLM acts as a test author, rewriting the instruction into a precise scenario — task grounded in the site map's real screens/elements (`sliceForAuthoring`: compact route index + term-matched page detail, empty-element pages excluded), manifest accounts referenced by name; credentials detected in the instruction are auto-registered via `secrets.ts` and mechanically scrubbed from the scenario, concrete fictitious form data, mandatory final verification, same language as the author. Authoring also sees existing scenarios (id + task) and suggests `depends_on` when the instruction presupposes a state another scenario produces (suggestions filtered against real scenario ids). Mechanical normalization mirrors the planner's sanitize: kebab-case id (unique via suffix), `start_url` validated against known map routes (invented paths fall back to `/`), 1 short semantic retry. Output is a committed file for human review — authoring is assisted, execution is a separate phase. Spend recorded in the ledger as `kind: "authoring"`. |
| `metrics.ts` / `costs.ts` | Every run writes `.windup/runs/<ts>-<scenario>.json` (tokens, calls, model, per-action timing, executed plan, failure classification `network|verification|plan_invalid`). Prices are a dated per-model table; reports recompute from tokens so history stays correct. `estimateCostUsd` takes the provider too: **subscription providers** (`claude-code`) resolve to $0 — the tokens are real and stay in the ledger, but they are covered by the developer's own subscription, so Windup never invents a per-token price (and, crucially, never falls through to the fallback rate and bills them on paper). The price table stays honest — those models are absent because their per-token cost is unknown, not zero. Scan LLM spend is recorded as `scan-*.json` in the same ledger. `windup costs` aggregates: totals, free replays, scans, **per-provider** (records without `llm_provider` are inferred from the model name — `claude-*` ⇒ `claude-code`), per-model, per-scenario, authoring, last N — alternating between LLM vendors keeps per-vendor spend visible. **Wall-clock breakdown:** `duration_ms` splits `total` into `planning` (LLM, 0 on hit), `execution` (this scenario's actions), `dependencies` (the re-run `depends_on` chain), `setup` (context launch) and `navigation` (goto + load/hydration BEFORE the first action — isolated from `execution`, usually the real SPA time sink). Printed as `total=… (plan=… deps=… exec=… setup=…)` and in the `run:end` stream event; the HTML report renders a per-scenario reconciling bar (`setup · deps · plan · nav · actions · other`) and JSON a `duration_breakdown`, so "a 113 ms action took 3.6 s" resolves to setup+nav. Under `--concurrency` the leftover segment is labeled **`contention`** (idle wait for a slot, not work) and an **`active`** ms figure (own work, ~stable across concurrency) is shown so scenarios stay comparable; a per-case `duration_breakdown` (with `active`/`contention`) rides in JSON. A scenario's declared `requires` (data preconditions) also render in the report. The cache's promise is `$0` (no LLM), not "instant": wall-clock stays real-browser time, which the breakdown makes legible (and which the `depends_on` session snapshot targets). |
| `summary.ts` | **Post-run AI debrief** (`run --summary`, opt-in): one extra LLM call after the run turns the executed plan + per-action timings + anomalies (re-planning, sig mismatch, slow steps) + the final page's aria snapshot into a 3–6 sentence prose debrief in the task's language, quoting concrete observed values (prices, messages) literally from the snapshot. Never affects the run result (failures are warnings); cost tracked in `metrics.summary` and added to `estimated_cost_usd` but NOT to `llm_calls` (which measures planning). Off by default so replays stay $0 in CI. |
| `suggest.ts` | **Post-failure fix suggestion** (`run --suggest`, opt-in, fires only on a FAILED run): one LLM call acts as a senior QA engineer, comparing the executed plan + the failing step + the real final page (`failure_snapshot`, or a live capture) + the site map's known selectors, and returns a concrete, actionable fix to the scenario (wrong selector → real one, wrong target screen, missing step, timeout too short), grounded in the evidence, in the task's language. Never edits the scenario (curated knowledge stays the author's); cost in `metrics.suggestion`, added to `estimated_cost_usd` not `llm_calls`. This is the tool closing the author's learning loop — a red run becomes a specific edit. |
| `validate.ts` | **`windup new --validate`**: generate → RUN → on failure, feed the failure + the fix suggestion + the real page back into authoring (`refineFrom`) and regenerate under the same id, bounded (≤3 attempts). Delivers a scenario that already passed once, with a warm cache and the map enriched by the flow's real pages. The refine loop lives in authoring, never in `run` (which stays an impartial judge). Injectable generate/run deps for testing without a browser. |
| `errors.ts` | `WindupError` for expected failure modes (missing scenario/config, bad flag) — the CLI prints its message plainly; anything else prints its message plus a `WINDUP_DEBUG=1` hint for the full stack. No user ever sees a raw Node stack trace by default. |
| `runner.ts` (parallel) | `run --concurrency <n>` runs scenarios through a small in-process pool (`runPool`, order-preserving) over the warm browser singleton with isolated `BrowserContext`s. Runs share one `SiteMapStore` (passed via `RunOptions.sharedMap`, saved once at the end): JS is single-threaded, so concurrent synchronous map upserts never race. Per-scenario cache/ledger files are independent. Default concurrency 1 (unchanged behavior); measured ~2× on a mixed 11-scenario cache-replay suite at 4. **Prewarming (sequential only, on by default; `--no-prewarm`):** while scenario *i* runs, the CLI pre-launches the **fresh** context+page for *i+1* (`launchBrowser` off the critical path) and hands it to `runScenario` via `RunOptions.prewarmed` — a **one-shot** thunk, so isolation is unchanged (each scenario still gets its own clean context) and a `--retries` re-attempt or the snapshot `storageState` path launches fresh instead; an unused warmed session (early `--bail`/`--max-wall` stop) is closed. Moves the ~200 ms launch off the wait (`setup`→~0). NOT applied under `--concurrency > 1` (the pool already overlaps launches). Deliberate answer to "context pool": measured newContext ≈ 18 ms (reusing a *live* context would leak state for that), newPage ≈ 190 ms — so Windup prewarms a fresh context rather than reuse a dirty one. |
| `runner.ts` (resilient CI) | **`--retries N`** (`runWithRetries`): re-runs a scenario whose failure kind is transient (`network`/`verification`/`dependency`/`setup` — the `RETRYABLE` set) up to N extra times; `forbidden` is excluded (a deliberate `config.forbid` block is never a flake). First pass wins; a scenario that passes only after a retry is stamped `flaky` with `attempts` — surfaced (console `↻`, HTML `FLAKY N×` badge, JSON fields, `run:end` stream) so a laundered-green is impossible. Each retry is a full fresh-context run. **`--max-wall <seconds>`** (a suite gate, requires `--all`): the CLI checks a wall-clock budget before starting each job — sequentially it breaks the loop; under concurrency it passes a `shouldStop` predicate to `runPool` (stops pulling new tasks, in-flight ones finish, results compacted to what ran). Exceeding the cap **fails the build** (`skipped > 0` ⇒ non-zero exit) with a `⏱ … X/Y ran, Z not started` line — a runaway suite fails loudly instead of hanging the runner. **`--bail`** shares the same halt path: a flag flips on the first non-pass and feeds the same `shouldStop` predicate (sequential break / pool stop), for fast PR-check feedback. |

| `resolvers.ts` | **Dynamic values (#resolve):** runtime-only values (OTP codes, magic-link URLs) declared in `config.resolve` and referenced by a plan via `value_ref: "<name>"` (fill) or `url_ref: "<name>"` (goto). `runResolver` fetches the source — `cmd` (shell stdout), `http` (fetch) or `fn` (a project module's `async () => string`) — polls until non-empty (default 30 s / 1 s), and `extractValue` pulls the value out via regex (capture group) or a JSON dot-path. Resolved lazily at the point of use and cached per run in the executor's `ResolverContext.vars`. **Security:** the SOURCE is author-declared, never LLM-emitted (no code-exec-from-model vector); the VALUE is ephemeral — used for the fill/goto and never written to cache, metrics or logs (the plan carries the reference name, not the value — same discipline as `ENV:` credentials). The planner is told the available resolver names so it emits `value_ref`/`url_ref` instead of a literal. **Reliable binding:** since the LLM can't be trusted to always emit `value_ref`, `config.resolveFields` maps a SELECTOR SUBSTRING → resolver name; the executor fills ANY matching field from that resolver, overriding whatever the plan put there (literal or mis-named ref) — deterministic, the point of a CI test. Ref names are normalized (`OTP_CODE`/`otp-code` → declared `otp_code`) and the schema tolerates that casing so a stray form doesn't `plan_invalid`. A `goto` may carry `url_ref` instead of `url` (validation updated). |
| `hooks.ts` | `setup`/`teardown` shell commands run OUTSIDE the cached plan (so they run on every replay): fixtures / cleanup for non-idempotent writes (a CREATE with a non-reusable unique key fails on replay otherwise). Two scopes, same `runHooks`: **per-scenario** (scenario JSON) — setup before the scenario+dependencies (failure → run fails, kind `setup`), teardown always in the finally (failure → warning); and **suite-level** (`config.suite.setup`/`teardown`, CLI-wired) — run ONCE around `run --all`, setup before the first scenario (failure → abort the suite, exit 2, no scenario runs), teardown in a finally after the last (failure → warning) — the beforeAll/afterAll analogue for a shared fixture DB or stub. ## 4. Data formats

**Action plan** (`plan_version: "0.1"`): `{ plan_version, scenario_id, task, start_url, generated_by, actions[] }`; action = `{ id: aN, type: goto|click|fill|wait_for|use, target?: {selector, description}, value? | value_ref? ("ENV:VAR", runtime-resolved, never persisted resolved), url?, use?, expect?: {selector?, url?, selector_value?, text_contains?, count?, not_visible?, attribute?}, timeout_ms }`. Semantic rules: click/fill/wait_for require `target.selector`; fill requires exactly one of value/value_ref; `value_ref` must be mentioned by task/hints/manifest (no invented ENV names); the final action must carry `expect` (or be a `use`, whose fragment carries its own postcondition), **and that `expect` must be able to fail** — `trivialExpect` rejects a final postcondition whose only assertion is the visibility (or absence) of a LANDMARK (`body`/`html`/`:root`/`main`/`div`/`section`/`#root`/`#app`/…), because such a plan passes whenever the page loads: a false green indistinguishable from evidence. Any content/value/count/attribute/url assertion discriminates and is accepted on any selector (`text_contains` on `main` is fine — the assertion is the text). The tag blocklist is only the cheap OFFLINE half: the planner additionally counts matches **on the live page** (`bareSelectorAssertion` → `browser.count`) and rejects a bare visibility assertion whose selector matches **>1 element**, since `h2` on a page with five headings survives deleting the whole section (evidence from the page under test beats guessing from the tag name; also covers `li`/`a`/`button`/`p`). Rejection routes through the ordinary semantic-retry path, with the match count in the error; the planner prompt carries a matching "the final expect MUST be able to fail" rule with BAD/GOOD examples, and the retry prompt additionally forbids reusing the action's own `target.selector`. **Deterministic repair before validation:** when the task quotes a literal (`taskLiteral`) and the final check is bare visibility, `assertTaskLiteral` rewrites it into `text_contains` on that literal — no LLM call — but only after confirming the live page contains the text, so the repair can never manufacture a failing test (a landmark selector is dropped, a specific one kept and ANDed). This is what keeps the guard from turning a false green into an unauthorable scenario. Deliberately validated at PLAN time only (planner + `record`), never on replay, so already-cached plans keep running — `windup explain` flags a cached weak verification instead. Two schema variants exist by necessity: a relaxed one for Gemini's `responseSchema` (no `const`/`pattern`/`maxItems`) and the full JSON Schema for local Ajv validation — **Ajv is the authority**.

**Scenario dependencies** (`depends_on: ["login"]`): prerequisites execute in the same browser session before the scenario, resolved as a deduped chain (cycle detection, depth ≤ 5), each with its own cache/replay/self-healing (a dep that re-plans re-caches under its own id; deps don't write their own ledger records — they ran as setup). A dependent scenario without `start_url` skips the initial goto and **continues from the dependency's final page — including at planning time**, so the planner snapshots the real post-dependency screen instead of planning blind — and its prompt switches to continuation mode: navigate by clicking in-app links, never `goto` (a full reload can drop SPA session state; observed live). A dependency that re-plans never leaks its partial result into the dependent run (a leaked "passed" produced a false green once — reset is mechanical). On any failed run the final page's aria snapshot is persisted as `failure_snapshot` in the ledger record (capped), turning post-mortems from guesswork into reading. Dependency failure fails the run with kind `dependency`. Cache hits additionally require the stored plan's `task` to match the scenario's current task (editing a task is a different test → miss). `metrics.dependencies` records the chain per run; reporters surface it.

**Cache entry** (`cache_version: "0.2"`): `{ key: {scenario_id, start_url(path), start_sig?}, plan, status: active|stale, stats: {created_at, last_replayed_at, replay_count, replay_failures, plan_generation} }`.

**Site map** (`map_version: "0.1"`): `{ last_scan_sha, pages: {sig → {urls_seen, url_pattern, title, interactive[], source, first/last_seen, seen_count, files?, stale?}}, transitions: [{from, action, to, seen_count}], assist_seen: {file → contentHash} }`.

## 5. Model & cost posture

Default planner model: **`gemini-3.1-flash-lite`** (measured: 1 clean call/generation, ~3–4s, ≈ $0.0025/generation; selected by A/B against 3.5-flash which degenerates and costs ~34×). Known pathology handled defensively: flash-family structured output can degenerate into token loops (non-deterministic per prompt content) — mitigated by transient retries with varied seeds, `maxOutputTokens` caps, short semantic-retry prompts, and near-constant prompt size budgets. Provider-agnostic since 0.10: Google Gemini and OpenAI ship in-box behind the `llm.ts` boundary, several providers can be configured at once, and any run/bench/scan picks one with `--llm provider[:model]` (`WINDUP_LLM` in CI). Since 0.21 an opt-in third provider, `claude-code`, lets developers plan through their own Claude subscription — by default (0.22) spawning the native `claude` CLI they already have (zero setup, no server), or routing to a third-party local wrapper when a URL is configured. Subscription-billed, so its ledger cost is $0 by design (§4 boundary), never a default. Every ledger record carries provider+model; prices are a flat per-model table (model names are globally unique) except subscription providers, which are $0. Adding a vendor = one client implementation in `llm.ts`.

## 5b. Security posture

Page content captured from the app under test (accessibility snapshots, element lists, final-page snapshots) is fed to the LLM for planning, summaries and fix suggestions — always **delimited and marked as untrusted data**, with an explicit instruction to treat it as data, never as instructions. Because plans are schema-validated data executed deterministically, a page cannot make Windup run arbitrary code; the residual risk is a crafted page biasing a generated plan or summary (run against apps you control, in test environments). Credential values never enter scenarios, plans, the cache or LLM prompts (`value_ref`, resolved at run time). Within `.windup/`, the committed dirs (`cache/` plans, `map/` site map) are secret-free and portable; the gitignored dirs hold the sensitive/ephemeral bits — `state/` (auth cookies/tokens), `runs/` (ledger), `reports/`. Full threat model in [`SECURITY.md`](../../SECURITY.md).

## 6. Known limitations / debts

- Nested react-router relative paths are collected best-effort (flat, not joined) — corrected by execution observations.
- Scan is single-package aware; monorepos are detected and warned, per-app indexes are future work.
- Dynamic crawl (SPEC-002 optional layer) not built — executions feed the map instead.
- No daemon between CLI invocations (deliberate); warm pool is per-process. Revisit only if p50 regresses.
- `page_signature` ids that encode data (`#add-to-cart-<product>`) split page states into distinct nodes — in practice this documents state variants, but it is unmeasured on data-heavy catalogs.
- Fragment auto-detection (common prefixes) not built; extraction is manual.

## 7. Verification

- `npm test` (packages/windup): ~97 unit/integration tests, LLM-hermetic (fakes; adapter seeds a known-good plan). CI runs them with real Chromium on Ubuntu.

- Real-project dogfood: react-router app with 106 routes — scan populates ~100 route nodes with clean elements; first real scenario planned with map-sourced selectors and replays at ~0.5s/$0; plan cache proven portable across ports/environments.
